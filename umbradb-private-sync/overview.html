A phone syncs its shielded coins without showing which are its own

Every phone downloads the same public files and finds its coins in them. It then reads what it needs with requests the server cannot read, at a block height it names. A phone that knows its date downloads only from that date on, and each new block reaches it over a WebSocket within seconds.

A phone follows its Dust without showing which coins are its own

Each Night output a phone holds starts a chain of Dust coins: every fee it pays spends the chain's current coin and creates the next. The phone follows its chains through a public file of spends, reads its first coins with private fetches, and checks each chain's last coin by reading its group, which also gives that coin's path. To pay a fee it reads one more group, in the tree of Night records.

What the server holds, and does at every block

Two sync modules of UmbraDB, one for shielded tokens and one for Dust, each with its own tables and its own height. Either runs without the other.

At every blockevery 6 seconds
  1. Each table takes the block's new records. New records fill one block of 2,048 columns before the next, so a block of the chain usually changes one block of columns per table, and compile redoes it in 0.32 s (below).
  2. Once every table has the new height, the module publishes it at once, with its manifest: roots, the open part of the group roots, and the digests of every file chunk and block of columns.
  3. The same WebSocket message goes to every connected phone: the new commitment entries, nullifier prefixes, Dust spends and first-coins map entries.
The last 20 heightstwo minutes
  1. A private fetch names its height. The current tables are in memory; each of the 19 before is a record count and the files of its changed blocks of columns, on disk.
  2. An older height is answered from the current tables with the newer records taken back. A height outside the window is refused with a standard HTTP error that says where the latest setup data is.
Growingpast one table's limit
  1. A table holds at most 230 cells. When one would pass it, a second table takes half of its records, chosen by a hash of their positions; then a third takes a third of each, and so on.
  2. Every table always holds an even mix of old and new records, and a call sends the same number of requests to each, so which table is asked says nothing of a coin's age. The first split comes near 22 million outputs.

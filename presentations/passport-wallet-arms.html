The idea

Your wallet is a device of the account

Any wallet with a key on these curves that signs the format works. No address of it on chain.

The core idea

Two curves, different wrappings

ECDSA / SECP256K1

EVM

The wallet signs a 32-byte digest. The format computes it.

EIP-712 typed data (approvals) keccak256(0x19 0x01 ‖ domain ‖ hashStruct(msg))
personal_sign, EIP-191 (blind requests) keccak256("\x19Ethereum Signed Message:\n" ‖ len ‖ text)

ED25519

Solana, NEAR, Cardano

The wallet signs the message itself (SHA-512 runs inside the signature). The format decides the bytes.

Solana signMessage, raw (today) raw header ‖ text, the bytes as given
Solana off-chain message (today) 0xff ‖ "solana offchain" ‖ v1 ‖ signer ‖ text
NEAR, NEP-413 (next) SHA-256(Borsh(tag ‖ message ‖ nonce ‖ recipient))
Cardano, CIP-8 (next) CBOR ["Signature1", header{address}, "", payload]

The core verifies a curve. The format is the chain's wrapping.

evm_k256

The EVM arm

K256Core

ECDSA over a 32-byte digest. r and s non-zero, the point at infinity refused, both S forms accepted.

EvmIdentity

The address: the last 20 bytes of keccak256(x ‖ y), coordinates big-endian, no 0x04 prefix.

Eip712V1

keccak256(0x19 0x01 ‖ separator ‖ structHash). The separator is a circuit constant.

EIP712Domain( string name, string version, address verifyingContract) name "Midnight Passport" version "1" verifyingContract 0x596e…104F no chainId, no salt

No chainId: the wallet signs on whatever network it has active. Every struct names the account, so an approval cannot move to another one.

sol_ed25519

The Solana arm

Ed25519Core: RFC 8032 with SHA-512 in the circuit, canonical encodings, A and R not the identity, S below the group order.

The same 16 circuits take both. The chain never learns which wallet signed.

A signature in one form fails in the other. The client never asks a wallet for a form it cannot sign: an unknown wallet is tried raw first, then off-chain.

The budget

Every circuit at k ≤ 18

k 19

EIP-712 and personal_sign in one circuit. So EVM approvals are EIP-712 only.

16 per arm

A full account with every arm, 84 circuits, deploys in 18 waves.

237,636

Rows of the worst NEAR or Cardano case measured: the next arms fit too.

One account

Any mix of devices

Any device adds any other

An EVM device adds a Solana device by its readable descriptor, and the reverse. The approval shows the new key in full.

Grants cross arms

An EVM device grants a scoped spend to a Solana wallet, which signs its own spends.

One nonce for all

Every device-gated call advances the same counter, so an approval prepared before another device's call is stale.

Privacy

Private by design

No address on chain

A device is stored as a hash. Only someone who knows the key and the blind can find it.

SHA-256(tag ‖ account ‖ key ‖ blind ‖ epoch ‖ counter)

The blind comes from the wallet

A hash of a deterministic signature over a blind request. Signed twice at enrolment, cached, and derived again on restore.

SHA-256(tag ‖ canonical signature)

One use, then it rolls

Each call replaces the device's entry with its successor and advances the nonce. An approval works once.

counter → counter + 1

The client checks the signer before proving. Two installed extensions can answer for each other, so a signature that does not verify under the expected key is refused before anything is sent.

Extension points

Adding an arm

E1Tag registry

A new arm is five tags (device, boot, grant id, blind, salt) and one registry entry naming its key class.

E2Key classes

Two today: a k256 key known by its 20-byte address (EVM) and an Ed25519 key (Solana). Their derivations take the tag, so nothing hard-codes a chain; a new key shape adds a class.

E3Enrolment kinds

One entry per kind of device an arm can add: a typed-data type (EVM) or a key text (Solana).

E4Text pieces

Shared renderers for numbers, hex, base58 and labels. Each arm writes its own frame.

E5Format seam

Each arm's seam reaches its format and its core (K256Core or Ed25519Core) through fixed interfaces only.

E6Client lists

Signer registry, blind schemes and the deploy list: one entry each.

A new arm on either curve is new files plus registry entries, not a redesign.

Next

NEAR, Cardano, and beyond

NEAR nea_ed25519

The wallet signs SHA-256 of a Borsh payload holding the text, so the core verifies over 32 bytes. The device is the key: binding a name such as batata.near needs NEAR state on Midnight, a cross-chain proof. Ledger NEAR shows the first 400 bytes.

Cardano cdo_ed25519

CIP-30 signData through the reward address; the circuit rebuilds the CBOR Sig_structure. Binding the address to the key needs BLAKE2b-224, which Compact does not have yet: until then the arm is test only.

Beyond: recovery straight to a wallet (one recovery gate per device scheme, as MIP-0022 plans); Ledger clear signing for the fixed EIP-712 domain (ERC-7730); BLAKE2b in Compact.

next: NEAR

NEAR walletsarm planned

To bind a NEAR name such as batata.near, Midnight needs NEAR state

The key is verified todayNEP-413 is Ed25519 over SHA-256 of a Borsh payload, so the core already checks the signature. The device is the key.

Named accounts need a cross-chain proofA name is a NEAR account that holds access keys, and those keys can change. Proving that a key belongs to the name needs NEAR's state on Midnight: a light client, a bridge or an oracle.

Implicit accounts need nothing moreAn implicit account's id is the hex of its Ed25519 key, so it follows from the key alone.

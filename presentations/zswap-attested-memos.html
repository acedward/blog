Outcome: authenticated off-chain metadata with unchanged consensus objects.
Problem

The problem is not carrying bytes. It is earning trust.

01

An offer moves value

A ZSwap offer can be relayed and merged, but the base format carries no trusted human message.

02

A plain sidecar is forgeable

Anyone can attach, alter, or re-attribute unsigned metadata. Displaying it as trusted creates a spoofing surface.

03

Putting it on chain is expensive

Adding a memo to the ledger format cascades through version tags, fee sizing, activation logic, wallets, and indexers.

Design target: cryptographic attribution with zero consensus change

Fail-closed construction: every cheap refusal happens before proving. Failure emits no file and never drops the requested memo.

Privacy

Why the proof does not leak the spender's identity

Verifier learns

  • Memo plaintext, intentionally visible in the file
  • Carrier nullifier already visible in the enclosed offer
  • Commitment C, recomputable from public file contents
  • Whether the proof and enclosed offer validate

Verifier does not learn

  • Spending secret
  • Public key or new identity handle
  • Coin nonce, token type, or value
  • Merkle path, balance, or ownership metadata
Zero knowledge hides the witness. It does not hide the memo, and it does not make authorship deniable to someone holding the file.
Implementation

Key code changes: one standalone crate, six clear boundaries

memo.rs + packing.rsValidate 1..=512 bytes and injectively pack length + 31-byte chunks.
commit.rsHash exact offer bytes and derive the shared context commitment C.
circuit.rs + circuits/Assemble the 7-field witness, 3-field statement, and nullifier equation.
container.rsCanonical ZSWPMEMO v1 codec with hostile-length and trailing-byte rejection.
attest.rs + verify.rsFail-closed construction and ordered trust-aware verification.
cli.rs + e2e/attest, verify, inspect, safe carrier-file input, and unmodified-node settlement.
Upstream ledger and node: unchanged
CLI

The user flow is three commands with distinct trust semantics

$ zswap-memo-attest attest \
  --offer maker.offer \
  --memo-file note.txt \
  --carrier-file carrier.txt \
  --out maker.zswpmemo

$ zswap-memo-attest verify maker.zswpmemo
$ zswap-memo-attest inspect maker.zswpmemo
attestWrites only after every check and proving succeeds.
verifyOnly this command may report AUTHENTICATED.
inspectStructural dump only. Authenticity is NOT CHECKED.

Use --carrier-file to keep the spending secret out of shell history and process listings.

Trade-offs

The approach is strong on attribution, weak on delivery guarantees

Advantages

  • No ledger, transaction, node, fee, or activation change
  • Authorization by the actual input spending secret
  • Exact memo bytes bound to exact offer bytes
  • No public key or coin attributes disclosed
  • Offline, fail-closed verification

Limitations

  • Relays can strip the memo and proof
  • No on-chain delivery, history, revocation, or uniqueness
  • Plaintext can leak content and writing style
  • About 5.3 KB plus framing
  • Tooling and verifier keys become a distribution surface

It demonstrates

The exact offer and submitted transaction bytes are unchanged, so normal node validation and settlement still apply.

It does not demonstrate

Node awareness of the memo, strip resistance, or interchangeability between the attestation and spend proving backends.

Recommendation

When attribution matters more than guaranteed delivery

Use it when

  • offer files already move off chain
  • the recipient can run a verifier
  • avoiding a coordinated hard fork matters
  • stripping is an explicit, acceptable risk

Do not use it as

  • proof that a memo was delivered
  • proof that no memo was ever sent
  • a permanent audit trail
  • an identity signature for a person or organization
One proof, one carrier nullifier, one exact memo, one exact offer file.That narrow claim is why the design is useful, reviewable, and deployable without consensus change.

Authenticated memos without a hard fork

The problem is trust, not carrying bytes

ZSwap offers already move off chain. A plain sidecar can carry a message, but any relay could replace it or claim a different input authored it. Putting the field in consensus would solve delivery, but it would also trigger a versioned ledger and node rollout.

Offer alone

Moves value and exposes input nullifiers, but has no trusted human message.

Unsigned sidecar

Easy to deploy, but forgeable, alterable, graftable onto another offer, and re-attributable.

Design target

Bind exact memo bytes to exact offer bytes and one input's spending secret, without changing consensus objects.

Narrow claim: whoever created this proof knew the spending secret corresponding to this carrier nullifier when authorizing this exact memo for this exact offer file.

Canonical container

The original offer stays byte-identical

The container is versioned and bounded before allocation. It rejects duplicate or out-of-order sections, unknown section kinds, reserved bits, trailing bytes, and size declarations outside the published limits.

Exact-byte binding

The context commitment hashes the enclosed offer bytes directly. No normalization or reserialization step can drift.

Safe decoding

Every declared length is capped before copying. Canonical ordering gives one encoding for one logical file.

Stripping behavior

Removing the wrapper yields the original offer. That preserves compatibility, but means NoMessage is not proof that no memo was authored.

Proof generation

Construction fails closed before writing a file

The attester rejects cheap errors first, derives one public context commitment, proves ownership of the selected carrier, then emits the container only after the complete operation succeeds.

01

Validate

Memo size, offer parse, user-owned carrier, and offer well-formedness.

02

Hash

offer_hash = SHA-256(exact offer bytes)

03

Pack

Length field, then 31-byte little-endian chunks.

04

Commit

C = transient_commit(packed memo, context)

05

Prove

Private coin fields + spending secret, public commitment + nullifier.

06

Encode

Pinned prover key and canonical v1 container. No partial output.

The same commitment function is called by construction and verification. This prevents the prover and verifier from silently choosing different byte packing or context rules.

Key implementation changes

One standalone crate, six reviewable boundaries

The prototype deliberately avoids changes to the ledger and node. Each module owns one invariant, while the CLI exposes different trust semantics for creation, verification, and inspection.

memo.rs + packing.rs

Enforce 1 to 512 bytes. Injectively encode length plus 31-byte little-endian chunks.

commit.rs

Hash exact offer bytes and derive the shared memo + offer context commitment.

circuit.rs + circuits/

Assemble the 7-field witness, 3-field statement, and nullifier ownership equation.

container.rs

Canonical ZSWPMEMO v1 codec with hostile-length, ordering, and trailing-byte rejection.

attest.rs + verify.rs

Fail-closed construction and the ordered trust-aware verification pipeline.

cli.rs + e2e/

attest, verify, inspect, carrier-file input, tamper checks, and unmodified-node settlement.

zswap-memo-attest attest --offer maker.offer --memo-file note.txt --carrier-file carrier.txt --out maker.zswpmemo
zswap-memo-attest verify maker.zswpmemo     # may report AUTHENTICATED
zswap-memo-attest inspect maker.zswpmemo    # structure only, authenticity not checked

Trade-offs

Strong attribution, intentionally weak delivery guarantees

This is a compatibility-first design. It gives a recipient evidence about authorship and file integrity without claiming the network has seen, stored, or preserved the memo.

Advantages

  • No ledger, transaction, node, fee, or activation change
  • Authorization by the actual carrier input's spending secret
  • Exact memo bytes bound to exact offer bytes
  • No public key or coin attributes disclosed
  • Offline, fail-closed verification
  • Original offer remains usable by existing tooling

Limitations

  • Relays can strip the entire memo + proof wrapper
  • No on-chain delivery, history, revocation, or uniqueness
  • Memo plaintext and writing style can reveal information
  • About 5.3 KB of proof plus container framing
  • Verifier and proving keys become distribution artifacts
  • Not a signature for a person or organization

Settlement boundary

Verify the wrapper, settle the original offer

After successful verification, tooling extracts the exact offer bytes and follows the normal transaction path. The memo and attestation are never serialized into the settlement transaction.

Authenticated ZSWPMEMO
Extract exact offer bytes
Build normal transaction
Unmodified node validates and applies

Use it when

Offer files already move off chain, the recipient can run a verifier, avoiding a coordinated hard fork matters, and stripping is an accepted risk.

Do not use it as

Proof of delivery, proof that no memo ever existed, a permanent audit trail, or a public identity signature.

One proof, one carrier nullifier, one exact memo, one exact offer. The narrow claim is what makes the design useful without consensus change.
